# Отказоустойчивость резервного копирования

## Аудит v0.6.1

Матрица отражает пути выполнения в исходном коммите `28d46c7`. Для SIGTERM предполагается штатный запуск службы через systemd. Результаты испытаний новой версии приведены отдельно.

| Стадия | SIGTERM | SIGKILL или потеря питания | Потеря сети, источника или диска | Что сохраняется и что запустится снова |
|---|---|---|---|---|
| Планировщик и SQLite | Контекст отменяется. Планировщик ждёт синхронного исполнителя, после чего отдельно фиксирует прерванный запуск | SQLite откатывает незавершённую транзакцию WAL. На старте открытые попытки помечаются `interrupted` | Ошибка предзапуска при отсутствии источника или хранилища может перенести план на пять минут. Остальные ошибки завершают запуск до следующего расписания | Поглощённая ручная заявка теряет происхождение. Восстановление сбрасывает плановое время активной задачи на момент старта службы |
| Локальный источник | Restic получает SIGINT и до 30 секунд на выход | Возможны недописанные блоки, нативный снимок или блокировка Restic | Нет предварительной привязки локального каталога к точке монтирования. Ошибка чтения Restic с кодом 3 отклоняется | Нативный снимок без манифеста в каталоге не появляется |
| SMB2/3 | Контекст передаётся библиотеке, но отложенное отключение использует фоновой контекст | Остаётся частично заполненный staging | Нет явного срока подключения и прогресса в capture. Успех требует завершения обхода и хотя бы одного файла | `capture_failed` после ошибки передачи. Автоповтора этой операции нет |
| SMB1 | `CommandContext` останавливает smbclient. Служба проверяет выход и итоговые счётчики tar | Частичный tar остаётся в staging. systemd контролирует процессы службы | Нет отдельного контроля прогресса tar. Неполный архив или отклонение счётчиков приводит к ошибке | Снимок не публикуется. Следующая попытка по обычному расписанию |
| SFTP | TCP dial отменяем. SSH handshake и последующие SFTP-вызовы не прерываются закрытием транспорта по контексту | Остаётся частичный staging | TCP dial ограничен 15 секундами. Установившийся, но зависший SSH/SFTP может остановить исполнитель на неопределённое время | Ошибка чтения завершает capture. Смена ключа хоста блокирует подключение |
| PostgreSQL | `CommandContext` завершает pg_dump или pg_restore | Остаётся частичный dump | `PGCONNECT_TIMEOUT=15` ограничивает подключение. Stall при уже установленной сессии отдельно не отслеживается | Снимок требует успешного dump и читаемого TOC |
| PostgreSQL для 1С | Прерываются pg_dump, COPY и сессия, удерживающая экспортированный MVCC-снимок | Остаётся частичный staging. Сессия и транзакция прекращаются, когда сервер обнаруживает разрыв | Присутствуют 15 секунд на подключение и отдельный SQL lock timeout. Нет контроля прогресса dump/COPY | Для публикации нужны успешные TOC, COPY и контрольные суммы. Ошибка не планирует отдельный повтор |
| Restic backup и verification | Restic получает SIGINT, затем принудительное завершение. Cleanup запускается после возврата исполнителя | Возможны блокировка и нативный снимок с `bh-pending` без подтверждения полноты | Ошибка Restic или проверки завершает запуск. Конфликт блокировки диагностируется отдельно | Незавершённый снимок не виден в BackupHub. Автоматического unlock нет |
| Манифест Restic и SQLite | Ошибка после записи манифеста может прервать фиксацию каталога | Манифест может быть полностью записан при отсутствии строки SQLite. Отдельное окно существует после записи строки и до завершения попытки | Повтор после восстановления не проверяет существующий манифест исходного запуска | Восстановление индекса способно прочитать манифест, но планировщик создаёт новый снимок |
| Staging | Удаление посредством defer после capture или попытки | Defer не исполняется. Связи каталога с конкретной попыткой нет | Очистка может молча завершиться ошибкой | Частичные каталоги могут оставаться на диске |

При потере диска назначения до захвата предзапуск v0.6.1 откладывает плановую дату либо оставляет ручной запуск без отдельного повтора. При потере диска после предзапуска журнал получает общий код ошибки захвата, Restic или SQLite, если каталог доступен. Конечное состояние заменяет значение стадии. Если исчез сам том каталога, обновить журнал невозможно до возврата SQLite. Штатная проверка доступности SQLite и локального каталога не зависит от сетевых сессий удалённых источников.

## Поведение после изменения

Политика повтора действует на логическую операцию. По умолчанию интервалы составляют 30, 60 и 90 минут после завершения предыдущей попытки. Время допуска хранится в SQLite с точностью до секунды. Штатная остановка и восстановление после SIGKILL сохраняют номер попытки, её этап и исходное расписание.

| Условие | Поведение |
|---|---|
| Источник, сеть или диск временно недоступны | Попытка завершает работу и освобождает место в очереди. После своего срока задание допускается повторно |
| Ошибка постоянна или лимит исчерпан | Операция завершается с диагностикой. Дальнейшие плановые и ручные запуски остаются доступны |
| Restic записал только дерево, до верификации дело не дошло | Снимок `bh-pending` остаётся в Restic и отсутствует в истории BackupHub |
| Дерево проверено, публикация прервана | SQLite хранит контрольную запись проверенного дерева. Повтор может использовать это дерево для публикации |
| Манифест опубликован, SQLite не зафиксирована | Служба ищет маркер по ID исходной операции, сверяет его с контрольной записью и читает дерево Restic. Фиксация SQLite идемпотентна и сохраняет связь с попыткой |
| SQLite зафиксирована перед остановкой | Служба подтверждает существующую запись по тому же маркеру и завершает операцию без второй копии |
| Staging недоступен или право владения не подтверждено | Удаление откладывается. Для очистки нужны запись попытки, исходное монтирование и совпадающий токен внутри принадлежащего ей каталога |
| Restic вернул конфликт блокировки | Операция останавливается с `restic_repository_locked`. Блокировка сохраняется |
| Основной процесс завершён принудительно | Дочерние процессы Linux получают сигнал завершения от ядра. Унаследованная файловая блокировка препятствует запуску нового экземпляра до закрытия их дескрипторов |

Обычные уведомления о готовности, освобождение исполнителя и время индивидуального допуска пробуждают планировщик. Диспетчер обслуживает до двух разных репозиториев одновременно. Подробности порядка допуска есть в [документации планировщика](scheduler.md).

## Настройка ожидания

Для пакетной установки параметры задаются в `/etc/backuphub/backuphub.env`. Примените изменения перезапуском службы. Длительности от `1s` до `24h` задаются в синтаксисе Go.

| Переменная | По умолчанию | Применение |
|---|---|---|
| `BACKUPHUB_CONNECT_TIMEOUT` | `15s` | SMB2/3 и SSH вместе с рукопожатием, ожидание запросов SMB1, подключение libpq и ожидание блокировки таблицы PostgreSQL |
| `BACKUPHUB_IDLE_TIMEOUT` | `5m` | Отсутствие прогресса захвата и вызовов Restic. Критерии зависят от стадии. Для SFTP используются сообщения подсистемы, для PostgreSQL рост архива или вывод COPY, для Restic метрики обработки дерева и чтение потока проверки |

## Ограничения

- Linux может удерживать процесс в непрерываемом ожидании ядра на отказавшем файловом устройстве. В таком состоянии резервирование остаётся занятым до выхода операции или перезагрузки.
- Удалённые деревья остаются полностью размещёнными во временном каталоге. Тайм-аут libpq применяется к соединению, а тайм-аут прогресса охватывает остановившуюся выгрузку. Длительный этап подготовки без наблюдаемого вывода может потребовать увеличить тайм-аут прогресса.
- Точка монтирования локального источника записывается при создании доступного источника. Для прежних и недоступных при создании источников она определяется при первом запуске с доступными данными. Служба не может восстановить конфигурацию отсутствовавшего на момент наблюдения тома.
- Сквозная сверка с маркером доступна для операций, начатых с новой версией. Прерванная попытка v0.6.1 сохраняется в истории и получает один догоняющий допуск. В старом переносимом манифесте нет ID исходной операции.
- Без манифеста проверенное или частичное дерево может занимать место в Restic. Ожидающие снимки не отображаются как успешные. Очистка каталога захвата охватывает попытки новой схемы с проверяемым владением.
- Для горячего подключения том должен снова стать видимым внутри пространства монтирования службы systemd. В VM возврат тома проверен с общим родительским монтированием `/mnt`. Если том виден только в пространстве хоста, автоматический повтор продолжит сообщать о его недоступности.
- Профиль 1С прошёл полную выгрузку, обрыв TCP и восстановление на PostgreSQL 17 с таблицей `public.config` и `bytea`. Отдельный прогон коммерческой сборки Postgres Pro для 1С остаётся открытым. Для установки Enterprise нужен [доступ к репозиторию поставщика](https://postgrespro.ru/docs/enterprise/17/binary-installation-on-linux).

Запускались `go test -race ./...`, `go vet ./...`, диагностика Svelte/TypeScript, веб-сборка и сборка Debian-пакета с SHA-256. Данные и сервисы проверялись в отдельных сетевых пространствах, контейнерах без внешней сети и Debian-VM. Сервер `tomas` и рабочие архивы в испытаниях не участвовали.

Повторить контейнерные испытания можно командой `tests/resilience/run-connectors.sh`. Для проверки установки, обновления, монтирования и питания используйте `tests/resilience/run-vm.sh /path/to/backuphub_0.6.1_amd64.deb` с проверенным пакетом v0.6.1. Скрипт печатает каталог журнала VM. Ему нужны Docker, QEMU/KVM и установленные зависимости веб-сборки.
