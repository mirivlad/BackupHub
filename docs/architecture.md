# Архитектура BackupHub

Источник истины по требованиям: [спецификация v0.1](specification-v0.1.md). Этот файл описывает границы модулей и текущую реализацию, а не заменяет требования.

## 1. Компоненты

```text
Браузер (Svelte/TypeScript — запланирован)
           │ HTTPS (Nginx либо встроенный TLS)
           ▼
BackupHub: REST API / RBAC / audit / export / restore
           │
           ├── Scheduler + orchestrator
           │       └── Job state machine
           ├── Connector registry
           │       ├── SMB2/3 (SMB1 — изолирован отдельно)
           │       ├── SSH/SFTP
           │       ├── Windows / WinRM / VSS
           │       ├── PostgreSQL / PostgreSQL Pro 1C
           │       └── Dovecot / IMAP / Thunderbird
           ├── Snapshot catalog + search (SQLite/WAL)
           ├── Capture / restore strategies + portable manifest
           ├── Storage adapter (предпочтительно Restic)
           │       └── Primary repo + independent secondary repo
           └── Secrets vault + privileged operation boundary
```

До реализации коннекторов API **не предлагает** создание фиктивных копий. Работающие HTTP endpoint сейчас: `/api/v1/health` и `/api/v1/system/identity`. Они **не** являются доказательством пригодности системы для резервирования.

## 2. Границы ответственности

- `internal/domain` — переносимые типы снимка, валидность составных копий, состояния запуска, чистый dry-run ротации.
- `internal/catalog` — SQLite/WAL и миграции; каталог восстанавливаем, не является единственным источником данных о снимках.
- `internal/connectors` — контракты обнаружения, проверки, подготовки, захвата, восстановления. Контракт не позволяет выдавать shell-скрипт вместо нативного плана.
- `internal/storage` — транзакция записи и чтение через адаптер защищённого репозитория. Выполнение destructive prune вынесено за пределы обычной записи.
- `internal/httpapi` — внешний REST и, позже, RBAC/audit/CSRF. Сейчас — только диагностические операции.
- `cmd/backuphub` — точка входа, конфигурация процесса, безопасный bind и остановка.

## 3. Неприкосновенные инварианты

1. Запись составного снимка — атомарная: отсутствующая обязательная часть блокирует commit.
2. Каталог может быть построен заново из переносимых манифестов и репозитория.
3. Доступ источника не предоставляет удаления или prune защищённого хранилища.
4. Ротация — отдельная привилегированная операция с dry-run, защитой hold и последней проверенной копии.
5. Метки `captured`, `data verified` и `restore verified` независимы.
6. Коннектор не объявляет app-consistent без соответствующего штатного механизма и проверки.
7. Экспорт файлов и восстановление приложений — разные сценарии; для приложения требуется совместимый restore recipe.
8. Нельзя скрывать fallback на непроверенный метод; старый скрипт не заменяет отсутствующий P0-коннектор.
9. Установка на каждой площадке автономна; `instance_uuid` предусмотрен для будущего fleet view.

## 4. Угроза и эксплуатация

Первый запуск реальных операций будет допущен только после секретного vault, bootstrap администратора, RBAC, защиты сеансов, аудита и изоляции опасных операций. Сейчас HTTP по умолчанию доступен только с loopback; разворачивать сервис с публичным портом запрещено. Не хранить пароли в SQLite sources.settings_json и в логе.

Restic — кандидат на backend, не доказанная интеграция. Её проверяют реальными backup/restore тестами до включения. Все форматы и restore recipe версионируются. Особый профиль PostgreSQL Pro 1C с binary COPY должен проверяться отдельно на целевом семействе версий.

## 5. Критерии качества

- `go test ./...` и `go vet ./...` проходят в CI.
- Любое изменение state machine и retention сопровождается тестами.
- Добавляемые коннекторы не принимаются по одному успешному backup: нужен тест восстановления и негативный тест.
- Системные тесты SMB1, VSS, AD и PostgreSQL 1C требуют отдельных тестовых стендов.
- Релизы не маркируются как готовые, пока соответствующие acceptance criteria из спецификации не подтверждены.
