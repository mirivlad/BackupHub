# Архитектура BackupHub

Источник требований: [спецификация v0.1](specification-v0.1.md). Описанное ниже разграничивает **текущий код** и целевое состояние.

## Компоненты и границы

```text
Браузер (Svelte/TypeScript)
           │ HTTPS (Nginx либо встроенный TLS)
           ▼
BackupHub: REST API / RBAC / audit / export / restore
           │
           ├── Auth + bootstrap + sessions (реализован базовый контур)
           ├── Vault AES-256-GCM + внешний master key (реализован)
           ├── Планировщик (cron, интервалы, ручные запуски)
           │       └── Журнал запусков в SQLite
           ├── Источники (локальный каталог, SMB1/2/3, SFTP, PostgreSQL и Postgres Pro для 1С)
           ├── Каталог снимков (SQLite/WAL)
           ├── Проверки хранилищ и пробные восстановления
           │       └── Расписания, очередь и результаты в SQLite
           ├── Просмотр файлов, ZIP и восстановление в новый каталог
           └── Restic (встроенный репозиторий и отдельные тома)
                   └── Снимки деревьев и переносимые манифесты
```

## Код

- `internal/domain` — переносимые типы снимка, проверка комплектности, состояния и чистый dry-run ротации.
- `internal/catalog` — SQLite/WAL, транзакционные миграции, схема v15 и постоянный instance UUID.
- `internal/auth` — Argon2id, локальный bootstrap администратора, сессии, базовый аудит.
- `internal/vault` — AES-256-GCM, ключ вне БД, отказ при утере ключа или повреждении данных.
- `internal/backup` — рабочий контур источников, Restic, копирования, истории и восстановления. Файловые снимки используют переносимый манифест дерева.
- `internal/connectors` и `internal/storage` — контракты для составных снимков приложений. В `internal/storage/restic` реализован отдельный адаптер составных объектов.
- `internal/httpapi` — HTTPS API для настройки, доступа, аудита, заданий, хранилищ и восстановления.
- `cmd/backuphub` — запуск службы, первичная настройка и [аварийное восстановление](recovery.md).

## Инварианты

1. Отсутствующая обязательная часть блокирует commit снимка.
2. Офлайн-комплект сохраняет каталог и ключи. Переносимые манифесты возвращают в восстановленный каталог снимки, записанные после контрольной точки.
3. Источник никогда не получает прав на удаление/очистку резервных копий.
4. Retention — отдельная привилегированная операция с dry-run, защитой hold и последней проверенной копии.
5. Создание копии, проверка данных и проверенное восстановление — три разные оси качества.
6. Коннектор не объявляет app-consistent без доказанного штатного механизма.
7. Восстановление приложения требует отдельного совместимого restore recipe.
8. Ключи и пароли не записываются в обычные настройки и логи.
9. Никаких legacy-скриптов вместо нативных P0-коннекторов.
10. Автономность каждой площадки гарантирована `instance_uuid`; fleet-view только в будущем.

## Проверки и изоляция

BackupHub сверяет дерево нового снимка с потоковым TAR до записи переносимого манифеста. Временный SQLite-индекс хранит пути и отметки обработки на диске, а исходные объекты дерева Restic дают байтовые имена и цели ссылок. При сбое после записи манифеста каталог можно восстановить через `backuphub recovery reconcile`. Снимок без метки commit остаётся ожидающим.

SQLite v13 добавляет таблицы `repository_check_schedules` и `verification_runs`. Проверка резервирует одно хранилище. Планировщик резервирует репозиторий до начала задания. Пока репозиторий занят, запланированное время и ручная очередь сохраняются. Длительная проверка одного репозитория позволяет планировщику выбрать задание для другого. Пул резервного копирования пока состоит из одного исполнителя. Служба выполняет до двух проверок на разных репозиториях; из них только одно пробное восстановление. Отдельная блокировка файла состояния исключает работу двух служб с одним каталогом. Штатная остановка отменяет дочерние процессы, а при загрузке БД незавершённые операции получают статус «Прервано».

Служба дублирует собственные записи `slog` в ограниченный буфер для администраторского API и продолжает писать в stderr для systemd. Проверки хранят диагностику в каталоге и показывают её рядом с результатом. Порядок запуска и лимиты описаны в [руководстве](verification.md).

## Текущие ограничения

Управление всеми пользователями, разграничение доступа по источникам, независимая репликация и защищённая ротация остаются в дорожной карте. Для восстановления нужны сохранившиеся репозитории. Храните комплект восстановления отдельно от узла и дисков с данными.

Сопровождающие тесты должны проверять не только успешные операции, но и удалённый ключ, повреждённый шифротекст, ошибочный bootstrap, доступ без сессии и запрещённое действие без CSRF.
