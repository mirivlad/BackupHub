# BackupHub — актуальная архитектура

**Срез к v0.1.0-preview.4, 10 ноября 2026 года.** Целевая спецификация: [specification-v0.1.md](specification-v0.1.md).

## Действующий состав

```text
Браузер Svelte 5 (русский интерфейс)
  └── HTTPS Go API: auth / CSRF / роли / аудит / настройка / экспорт / восстановление
       ├── Каталог SQLite/WAL, схема v6, постоянный instance_uuid
       ├── Vault AES-256-GCM, master.key, хранилище сетевых паролей
       ├── Планировщик интервальных заданий + журнал попыток
       ├── Коннекторы: local, SMB2/3, SSH/SFTP, обычный PostgreSQL
       ├── Захват → Restic file tree → проверка → независимый commit-маркер
       ├── Репозитории: primary + N внешних /mnt,/media,/backup,/backup2,/srv/backups
       │    ├── режим с ключом в /var/lib/backuphub/restic-<id>.key
       │    └── режим --insecure-no-password (без внешнего ключа)
       ├── Аварийное восстановление: Recovery Kit + чтение Restic commit-маркеров
       │    └── CLI восстановление SQLite/ключей в новый каталог; degraded primary
       ├── История: источники / file_snapshots / snapshot.repository_id
       └── Восстановление: скачать файл, ZIP или безопасно создать отдельный каталог
  └── Привилегированный storage-helper (systemd Unix-socket, только root)
       └── просматривает разрешённые смонтированные тома, создаёт приватные папки
```

## Границы ответственности

- **Catalog**: индекс и конфигурация; единственным источником истины о данных быть не может.
- **Restic**: физические блоки, снимки и данные. Режим выбран при создании отдельного репозитория и неизменен.
- **Portable commit marker**: отдельный Restic-снимок с `backuphub-tree-manifest.json`, тегом `bh-commit-<id>`, ссылкой на завершённый снимок `bh-pending` и исходным ID. Это не полный экспорт исходной конфигурации/паролей.
- **Source connector**: семантика копирования/согласованность. Для SMB/SFTP используются временные локальные staging-каталоги на выбранном backup-диске.
- **Storage-helper**: не имеет функции удаления, чтения содержимого архива, перезаписи владельцев существующих папок или произвольного командного исполнения.

## Безопасность и отказоустойчивость

- Вся работа с ключами требует приватных каталогов/файлов. Потеря `master.key` приводит к недоступности защищённых сетевых credentials; потеря Restic-ключа — к недоступности соответствующего парольного репозитория.
- Для `--insecure-no-password` внешний секрет не нужен, но любой получивший диск способен прочитать архив.
- Нельзя создавать новый репозиторий вместо исчезнувшего mount: проверка диска перед операциями и отказ при отключении.
- Только полноценный commit-маркер позволяет считать снимок завершённым. Не использовать произвольный `restic snapshots latest` вместо каталога BackupHub.
- Режим аварийного импорта в Preview 4 **не должен форматировать** существующий Restic-архив, перезаписывать файлы или без проверки объявлять незавершённые снимки готовыми.
- Импорт **полной** конфигурации выполняется из сохранённого Recovery Kit в офлайн-режиме; из одних Restic-маркеров восстанавливается только история завершённых снимков, без сетевых учётных данных и расписаний. При пропавшем primary сервер стартует в деградированном состоянии, не заменяя архив пустым.
- Автоматическое управление retention, репликация, полное управление ролями, Windows/AD/VSS, PostgreSQL Pro 1C и почта — последующие этапы.
