# BackupHub v0.1.0 Preview 1

**Первый устанавливаемый Debian/Ubuntu amd64 Preview для проверки базовых задач.**
Это не финальный релиз 1.0 и не подтверждённая система резервного копирования критичных серверов.

## Работает

- Один независимый сервер BackupHub на площадку; пользователь/администратор, сессии, мастер-ключ, аудит.
- Источники: локальные Linux-каталоги, сетевые общие папки **SMB2/3**, **SSH/SFTP**, обычный **PostgreSQL** в формате `pg_dump -Fc`.
- Ручные задания и периодическое расписание, постоянный журнал фаз, отказов и перезапусков.
- Зашифрованный репозиторий Restic, файловые снимки с датами, отдельный переносимый commit-манифест, контроль целостности.
- Просмотр версий, скачивание одного файла, папки или набора выбранных файлов и папок как ZIP, восстановление в новый каталог сервера без перезаписи источника.
- Svelte UI на русском, HTTPS-подключение, Debian-пакет с systemd-сервисом и отдельным пользователем `backuphub`.

## Установка и обязательная проверка

Скачайте `backuphub_0.1.0~preview.1_amd64.deb` и `.sha256`, затем:

```bash
sha256sum -c 'backuphub_0.1.0~preview.1_amd64.deb.sha256'
sudo apt install './backuphub_0.1.0~preview.1_amd64.deb'
sudo runuser -u backuphub -- backuphub bootstrap -data-dir /var/lib/backuphub
sudo systemctl status backuphub
```

В браузере: `https://<сервер>:8443/`. Сертификат из пакета самоподписанный. Сначала заведите администратора, добавьте **тестовый** источник, выполните резервное копирование, скачайте ZIP старого снимка и восстановите удалённый файл в новый каталог. Только после независимой проверки данных подключайте неважные рабочие сценарии. Для важных данных необходима независимая испытанная копия.

## Ограничения, важные до использования

- **PostgreSQL Pro 1C 16:** нативный split-config для `public.config` пока **НЕ готов**. Не назначайте такие базы обычному PostgreSQL-коннектору, если нужно гарантировать пригодную копию.
- **SMB1**, Windows VSS/AD System State, Thunderbird, Dovecot/IMAP/POP3 не поддерживаются.
- **SMB2/3 и SFTP** на Preview предварительно целиком загружают исходный каталог в staging-среду на backup-сервере. Убедитесь в достаточном объёме локального диска. Потерянные ACL/xattr не восстанавливаются; символические ссылки и неподдерживаемые объекты приводят к ошибке задания.
- Нет пока безопасной автоматической ротации/очистки Restic и независимой иммутабельной реплики. **Не применяйте вручную `restic forget` / `prune`: переносимые commit-манифесты ссылаются на отдельные снимки.**
- По умолчанию репозиторий хранится на backup-сервере. Отказ его диска уничтожит и основные данные, и копии, если не настроено внешнее хранилище.
- Потеря `master.key` лишает доступа к сохранённым источникам; потеря `restic.key` лишает доступа к архиву. Нужны защищённые независимые офлайн-копии ключей и данных.
- Восстановление поддерживается только в **новый** каталог на сервере BackupHub или путём скачивания. Автоматическое восстановление активной PostgreSQL-БД/SMB-шары на исходный хост не выполняется.
- Контроль `restic check --read-data` не является проверкой запуска восстановленного приложения. Для 1.0 нужен отдельный restore drill.
- Нет полного сценария восстановления каталога SQLite после разрушения экземпляра, все обязательные AT-сценарии ещё не закрыты.

Дальнейшие задачи — нативный Postgres Pro 1C split-config, полноценный файловый pipeline с ACL, защищённая ротация и копии в независимые репозитории, пакеты и end-to-end восстановление.
