# BackupHub: установка, несколько хранилищ и защищённый выбор каталога

> Начиная с `v0.1.0-preview.2`. При обновлении с Preview 1 старый
> репозиторий и все его снимки сохраняются.

## Ожидаемый пользовательский сценарий

1. Системный администратор скачивает `.deb` и выполняет `sudo apt install ./backuphub_….deb`.
2. Установщик создаёт отдельную непривилегированную учётную запись **backuphub**, нужные служебные каталоги, права, HTTPS-службу и systemd socket для ограниченного помощника файлового менеджера. Перезапуск или обновление **никогда** не удаляют ключи/снимки.
3. При интерактивной установке можно **по желанию** задать первый логин и пароль (пароль не передаётся аргументами или в Debian debconf). Если у apt нет терминала, установка не блокируется: после неё можно запустить:
   ```bash
   sudo runuser -u backuphub -- backuphub setup-admin -data-dir /var/lib/backuphub
   ```
   Альтернатива: существующий одноразовый bootstrap-токен и регистрация в веб-админке.
4. Администратор входит по HTTPS, открывает «Хранилища» и видит смонтированные тома под `/mnt`, `/media`, `/backup`, `/backup2`, `/srv/backups`, в том числе реальные объёмы свободного места.
5. Он раскрывает директории на нужном томе, выбирает существующую личную папку `backuphub` с правами 0700 или задаёт имя новой (например `BackupHub-Office`) и название хранилища («Диск 1»). Системный помощник создаёт новую папку с правами `0700 backuphub:backuphub` либо проверяет доступ к существующей, не меняя её владельца. Затем обычный процесс инициализирует внутри неё зашифрованный Restic-репозиторий.
6. В форме нового задания администратор выбирает **конкретное хранилище**: «Диск 1», «Диск 2», «Бэкапы PostgreSQL». Никаких глобальных ограничений одним путём.
7. Смена хранилища у существующего задания применяется **только к следующим снимкам**. Старые остаются на прежнем диске и выгружаются/восстанавливаются из исторически правильного репозитория.

## Файловая структура

```text
/var/lib/backuphub/
    catalog.db                  # пользователи, задания, маршрутизация, история
    master.key                  # ключ шифрования секретов источников
    restic.key                  # ключ встроенного репозитория (совместимость)
    restic-<storage-id>.key     # отдельные ключи добавленных репозиториев
    repository/                 # старое встроенное хранилище
/mnt/disk1/BackupHub-Office/
    repository/                 # первый внешний Restic
/backup2/BackupHub-Postgres/
    repository/                 # второй независимый Restic
```

Ключи каждого Restic, каталог SQLite и `master.key` должны входить в независимый комплект аварийного восстановления. Встроенный репозиторий `primary` сохраняется при обновлении со старой версии; автоматической миграции его содержимого на выбранный диск нет.

## Безопасность выбора места

Путь выбирается **на сервере BackupHub**, а не на компьютере, с которого открыт браузер. Браузер не может предоставить серверу доступ к локальному диску клиентского ПК через HTML file-picker.

Основной процесс продолжает работать пользователем `backuphub`, `NoNewPrivileges=true`, `ProtectSystem=strict`. Подготовка директории осуществляется root-помощником `backuphub storage-helper`, доступным только через локальный Unix-socket `/run/backuphub-storage.sock` с владельцем `root:backuphub` и правами `0660`. Отдельный помощник:

- не открывает TCP-порт и не принимает произвольных shell-команд;
- показывает только тома из проверенного `/proc/self/mountinfo` под разрешёнными корнями;
- открывает каждый компонент пути через `openat(O_NOFOLLOW)`, не следует по символическим ссылкам;
- может создать **новую** дочернюю папку с ограниченным именем (буквы, включая кириллицу, цифры, дефис, точка, подчёркивание) и передать права на неё `backuphub`, либо проверить уже существующий личный каталог владельца `backuphub` (0700);
- не имеет операций для удаления файлов, изменения прав существующих папок, просмотра содержимого файлов или самостоятельного копирования;
- не предлагает системный диск, замаскированные `/etc`, `/root`, `/var`, pseudo-filesystems, включая tmpfs/overlay. Если том не смонтирован — он не показывается.

Если нужно использовать `/backup` или `/backup2`, эти каталоги должны быть **точками монтирования** (или содержать смонтированные тома). Это намеренное правило: нельзя случайно заполнять системный диск при исчезновении внешнего хранилища. Для обычных не-монтированных папок потребуется отдельная осознанная политика в будущем.

Для удалённых SMB/SFTP и логических PostgreSQL резервных копий staging размещается на выбранном хранилище, внутри его отдельного защищённого каталога `staging/`; для встроенного `primary` остаётся `/var/lib/backuphub/staging`. Это исключает обычное переполнение системного раздела при использовании внешнего диска, но требует свободного места под полный временный захват.\n\nПри отказе уже зарегистрированного тома `openRepositoryNamed` запрещает его создание заново. Нет скрытой подмены диска, а задание получает ошибку. Старые снимки других хранилищ остаются доступны.

## Несколько репозиториев

Схема SQLite v5 содержит `storage_repositories` и `schedule_repositories`. Все существующие задания прежней версии связываются со встроенным `primary`, а путь основного репозитория записывается при старте с запретом незаметного изменения. Новое расписание/задание сохраняет собственный идентификатор хранилища; одна и та же площадка может использовать множество репозиториев. При фиксации снимка `snapshots.repository_id` обязательно сохраняет **фактический** репозиторий, использованный для записи.

Политики удаления/retention, защищённая репликация, автоматический перенос снимков между репозиториями и места хранения в S3 пока не входят в эту задачу. Уничтожать старые репозитории после изменения назначения нельзя.

## Приёмка

- Обновить базу v4→v5 без потери источников, заданий, снимков и ключей.
- Создать с помощью помощника два хранилища на двух смонтированных томах, проверить права и отсутствие доступа к произвольным системным каталогам.
- Создать источник на первом репозитории, сохранить снимок, сменить назначение на второй, сделать новый снимок.
- С исходным файлом, изменённым между снимками, скачать обе версии и восстановить каждую.
- Отключить второй том: BackupHub не создаёт «замену» на системном разделе, фиксирует ошибку; прежний снимок первого тома доступен.
- Перезапустить службу, проверить сохранность всех привязок и работоспособность web API.
- Проверить свежую DEB-установку, включая socket activation, и обновление существующей установки с данными.
