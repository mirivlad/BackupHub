# BackupHub — техническое задание и архитектурная спецификация

**Версия документа:** 0.1 (проект для обсуждения)  
**Дата:** 8 ноября 2026 г.  
**Тип:** концепция продукта, требования, архитектура, сценарии, план реализации и критерии приёмки  
**Рабочее название:** BackupHub; окончательное имя не утверждено.  
**Назначение:** основа для проектирования и разработки самостоятельного open-source продукта.

> **Главные решения:** никаких обязательных постоянно установленных агентов; первая полноценная версия использует собственные встроенные коннекторы, а не существующие Bash/cron-скрипты; пользовательские скрипты — только дополнительный механизм для нестандартных случаев; по умолчанию один независимый BackupHub на организацию/площадку; объединение нескольких узлов в одном интерфейсе — будущая функция.

## 1. Резюме

BackupHub — лёгкая система централизованного резервного копирования и восстановления для смешанных инфраструктур: Windows, Linux, Samba/SMB, PostgreSQL (включая особые базы 1С), почтовые серверы и локальные профили Thunderbird. Её задача — **обеспечить возможность получить нужное состояние данных за нужную дату и восстановить его понятным способом**, а не просто регулярно запускать копирование.

Система должна уметь собирать данные преимущественно без агентов через SMB, SSH/SFTP, протоколы БД и IMAP; использовать штатные удалённые механизмы Windows (WinRM, VSS, Windows Server Backup) там, где без локальных операций нельзя; обеспечивать хранение нескольких независимых во времени **логически полных** снимков, поиск исчезнувших файлов, восстановление и скачивание отдельных файлов, каталогов и выбранных наборов.

**Критерий успеха:** администратор способен установить один сервис на backup-сервер, подключить источники с помощью веб-интерфейса, настроить расписания и политику хранения, а через месяц без командной строки найти удалённый пользователем файл и скачать папку ZIP-архивом; восстановить базу 1С на отдельный сервер по поддерживаемому сценарию; проверить, что копии защищены от потери и удаления.

### 1.1. Принципы продукта

1. **Восстановление первично.** У каждого поддерживаемого типа данных есть явно определённые методы восстановления и проверки; «копия создана» не приравнивается к «восстановление проверено».
2. **Agentless-first, но без самообмана.** Постоянных агентов не требуется для большинства источников; если сценарий требует выполнения операций на источнике, применяются штатные удалённые средства ОС. Техническое ограничение явно видно администратору.
3. **Полноценные штатные коннекторы.** Никакой временной зависимости от пользовательских скриптов и cron в первой версии. Кастомные скрипты отдельно, как расширение.
4. **Исторические снимки.** Каждый снимок выглядит полным; физическая дедупликация допустима. Удаление или шифрование исходного файла не уничтожает его прежние версии.
5. **Простота эксплуатации.** Один сервис, встроенный веб-интерфейс, встроенная SQLite, минимальное число зависимостей; без обязательного Kubernetes, внешнего брокера или отдельного кластера БД.
6. **Предсказуемость.** В интерфейсе видно, что именно защищено, каким способом, когда было сохранено, насколько копия проверена и что останется после ротации.
7. **Независимость площадок.** Одна автономная установка на организацию; отказ другого экземпляра не влияет на неё.
8. **Возможность восстановления без BackupHub.** Стандартный формат хранилища, документированные процедуры, экспорт ключей/метаданных и аварийная CLI-команда; никакого закрытого незаменимого архива.
9. **Безопасность по умолчанию.** Разделение полномочий, секреты вне скриптов, изоляция SMB1, защита архива от удаления, аудит экспорта данных.
10. **Честные статусы.** Неполная копия не может отображаться как успешная; гарантии прав, VSS или IMAP не заявляются без проверки.

## 2. Реальные исходные сценарии

### 2.1. Организация А: смешанная сеть

- Windows- и Linux-хосты, SMB-шары разных поколений (в том числе SMB1 и SMB2), Active Directory.
- Пользовательские ПК с Thunderbird: нужны резервные копии почтовых профилей при доступности машины в сети.
- PostgreSQL Pro 1C 16 с базами 1С: `NEW_UT`, `NEW_ZUP`, `NEW_BP`. Обычный `pg_dump` всей базы не подходит в наблюдаемой конфигурации из-за очень больших значений в `public.config`.
- Сейчас используется разделение обычного SQL-дампа без `public.config`, отдельной схемы и `COPY ... WITH BINARY`; способ восстановления хотя бы однажды проверялся вручную. BackupHub должен реализовать этот сценарий **нативно**, с проверкой комплектности, совместимости и воспроизводимым восстановлением.
- Централизованный backup-хост, похожий по роли на `hp-back1`; удалённые данные поступают с файловых и SQL-серверов.
- Нужна история за разные даты, потому что сотрудники удаляют файлы с запоздалым обнаружением, а шифровальщик может испортить целую сетевую папку.

### 2.2. Организация Б: относительно простая сеть

- Samba-шара на Linux.
- Почтовый сервер с IMAP и POP3; при доступе к собственной почтовой инфраструктуре предпочтительна серверная копия почтового хранилища с поддерживаемым способом восстановления. IMAP — запасной или самостоятельный режим на уровне ящиков/сообщений, POP3 — ограниченный режим.
- Отдельный независимый экземпляр BackupHub и собственное хранилище/политики.

### 2.3. Повседневные истории, которые система обязана решать

**SC-01. «Файл удалили месяц назад».** Поиск по имени/пути и периоду; показать последнюю дату присутствия файла; открыть нужный снимок; скачать один файл или восстановить его в отдельный каталог.

**SC-02. Шифровальщик в общей папке.** Показать историю снимков, выявить массовое изменение как сигнал риска, закрепить последний заведомо исправный снимок, прекратить его автоматическое удаление, восстановить выбранную папку или всю шару. Система не должна считать «последний» синонимом «здоровый».

**SC-03. «Отдай папку Video на флешку».** Администратор открывает снимок на конкретную дату, отмечает `Video`, выбирает ZIP, получает архив через браузер и передаёт пользователю. Можно выбрать несколько произвольных папок/файлов из **одного снимка**.

**SC-04. ПК был выключен.** Плановое окно прошло; состояние «ожидает доступности» без ложного успеха; при возвращении ПК в сеть выполняется одно догоняющее задание согласно политике.

**SC-05. Сбой базы 1С.** Выбор заведомо пригодного комплекта резервной копии, выбор отдельной тестовой базы/сервера, подготовительные проверки, восстановление компонентов, контроль результата, журнал и отчёт. Восстановление поверх рабочей базы — отдельная опасная операция с повышенными правами и подтверждением.

**SC-06. Утерян backup-сервер.** Администратор с ключом и резервной копией конфигурации восстанавливает каталог, подключает стандартный репозиторий и получает данные без работающего прежнего BackupHub.

**SC-07. Постоянно доступный почтовый сервер.** Копия почтового хранилища без установки агента, с документированным способом возврата конкретного ящика и полной системы в рамках возможностей данного серверного продукта.

**SC-08. Несколько организаций.** Раздельные самостоятельные серверы и ключи. Между ними нет общей обязательной базы, облачной регистрации и единой точки отказа.

## 3. Границы продукта и обязательность

Обозначения: **P0** — требование к первому полноценному выпуску 1.0; **P1** — следующий расширенный выпуск; **P2** — перспектива. Модули внутри P0 можно разрабатывать поэтапно, но **публичный выпуск 1.0 не должен подменять отсутствующие P0-коннекторы запуском старых скриптов**. До готовности выпуска допускаются внутренние предварительные сборки с честным списком ограничений.

### 3.1. Матрица функциональности

| Область | P0 — первый полноценный выпуск | P1 / P2 |
|---|---|---|
| Развёртывание | Linux systemd + контейнерная установка с корректными привилегиями; один автономный экземпляр | Управление парком узлов P2 |
| Веб-интерфейс | Состояние защиты, источники, задания, история, журнал, поиск, экспорт, восстановление, настройки | Более сложная аналитика P1 |
| Доступ | Локальные учётные записи, роли, TLS через reverse proxy/встроенный сервер, аудит | LDAP/AD SSO P1, дополнительный MFA P1 |
| Linux | SSH/SFTP: файлы, каталоги, права и метаданные в пределах подтверждённых возможностей | Дополнительные FS-снимки P1 |
| SMB | SMB2/3 штатно; SMB1 в изолированном совместимом режиме; история и восстановление | Более широкие специфические ACL/ADS P1 |
| Windows | Удалённое копирование доступных файлов/профилей; WinRM/VSS для поддерживаемых режимов без постоянного агента | Полные образы ОС и автоматизированный bare-metal P1 |
| Thunderbird | Поиск профилей, копия полного профиля, режим согласованности и восстановление профиля на тестовом/целевом ПК | Сложное выборочное извлечение отдельных писем P1 |
| PostgreSQL | Логический дамп для обычных баз, отдельный нативный профиль PostgreSQL 1С с большими `public.config`, восстановление на отдельный сервер | Физические копии + PITR/WAL P1 |
| Почта | Dovecot (если обнаружен) и/или штатное серверное хранение через SSH; IMAP-бекап ящиков и экспорт сообщений; явные ограничения POP3 | Другие специализированные серверы P1 |
| Планировщик | Периодичность календарная/интервальная, доступность ПК, ретраи, исключение пересечений | Более сложные зависимости P1 |
| Хранилища | Локальное FS, SFTP, совместимое S3 и второй независимый репозиторий | Дополнительные backend P1 |
| История | Логически полные снимки, дедупликация, политики хранения, закрепление, поиск удалённых файлов | Аналитика изменений и расширенная эвристика P1 |
| Экспорт | Файл напрямую, папка/выборка ZIP/TAR, полная копия, большие скачивания с возобновлением для подготовленного экспорта | Нативное сохранение папок через браузер P1 |
| Восстановление | На исходный/иной путь, выборочно/полностью, preview, конфликты, проверка, безопасный режим | Автооркестрация сложных приложений P1 |
| Уведомления | Email, Webhook, Telegram, ChimePort через HTTP API | Дополнительные каналы P1 |
| Скрипты | Нет необходимости в них для штатных P0-сценариев | Пользовательские Bash/PowerShell задания P1 (опциональный коннектор) |

### 3.2. Что не обещаем в 1.0

- Скрытого автоматического восстановления любой Windows-машины «с нуля» на произвольное железо.
- Полной гарантии Windows ACL/ADS только по обычному SMB-чтению; у каждого метода должен быть явный уровень полноты метаданных.
- Транзакционной согласованности любой почтовой базы через IMAP или любого пользовательского приложения через файловую копию.
- Возможности достучаться до отключённого ПК вне доступной сети без VPN/маршрута/клиента.
- Универсального обнаружения шифровальщиков без ложных срабатываний.
- Неограниченного хранения без расчёта диска и внешней независимой копии.

## 4. Целевая архитектура

### 4.1. Концептуальная схема

```text
                    Браузер администратора
                             |
                         HTTPS/TLS
                             |
            +----------------------------------+
            | BackupHub (один основной процесс) |
            | Web UI + API + RBAC + аудит       |
            | Scheduler / Job Orchestrator      |
            | Source Connectors + Restore       |
            | Snapshot Catalog + Search Index   |
            | Storage / Export / Notifications  |
            +----------------------------------+
                |        |         |         |
               SMB      SSH      WinRM    DB/IMAP
                |        |         |         |
          Samba/Win   Linux/1C  Win/AD   PG/почта
                             |
                   Движок снимков Restic
                             |
               +-------------+------------+
               |                          |
         Основной репозиторий       Независимая копия
         (local/SFTP/S3)           (другой trust domain)
```

**Архитектурный стиль:** модульный монолит на Go. Встроенный интерфейс (Svelte/TypeScript), REST API, SQLite/WAL для конфигурации и каталога, Restic как базовый механизм защищённых файловых снимков. Нельзя встраивать напрямую в API/UI предположения о единственном архиваторе: между коннектором и хранилищем существует внутренний контракт объектов снимка.

**Обязательное разделение:**

- **Source Connector** — обнаруживает источник, проверяет доступ, читает данные/метаданные, выбирает способ получения согласованного состояния.
- **Capture/Restore Strategy** — описывает зависимые от приложения этапы резервирования и восстановления; запоминается с версией.
- **Transfer/Storage Engine** — отвечает за поток данных, хранение, проверку блоков, шифрование, репликацию.
- **Snapshot Catalog/Index** — показывает историю и обеспечивает поиск; данные каталога должны восстанавливаться из метаданных репозитория и переносимого манифеста.
- **Export Service** — потоковая/подготовленная выдача файла, дерева, произвольной выборки или целого снимка через HTTPS.
- **Scheduler/Orchestrator** — задания, повторы, блокировки, зависимости, прерывания, лимиты нагрузки.
- **Security/Audit** — роли, изолированные привилегии, ключи, протоколирование и подтверждения опасных действий.

### 4.2. Модель подключения без постоянных агентов

- **Pull:** для сетевых папок, файлов Linux, IMAP и большинства SQL-сценариев инициатором операции выступает BackupHub.
- **Remote execute (не агент):** одноразовый запуск строго типизированных и контролируемых команд через SSH или WinRM, когда это необходимо для VSS, серверного SQL-дампа, Dovecot или System State. На источнике не требуется постоянный демон BackupHub.
- **Опциональный помощник в будущем:** лишь там, где протоколы/права/сеть не позволяют гарантировать требуемый результат. Не обязательная часть 1.0, не скрытая предпосылка.
- **Старый SMB1:** отдельный процесс/изолированное окружение с отдельными параметрами протокола, сетью и правами. Нельзя понижать глобальную политику SMB всей системы.

### 4.3. Интерфейс коннектора (логический контракт)

Каждый коннектор предоставляет `discover`, `validate`, `plan`, `capture`, `verify`, `restore_plan`, `restore`, `cleanup` и декларацию `capabilities` (файлы, ACL, согласованность, отдельные объекты, удалённое выполнение, экспорт, версионная совместимость). `capture` возвращает поток файлов/объектов либо манифест согласованного набора — **не произвольный shell-код**. Внутренние этапы должны быть идемпотентны или иметь безопасный rollback, а отмена — очищать временные ресурсы.

Для каждого коннектора определяются: список версий ОС/ПО, режим аутентификации, требования к правам, ограничения, миграции формата, инструкция аварийного восстановления, тестовый набор с реальным восстановлением.

## 5. Жизненный цикл заданий

1. **Планирование:** с учётом часового пояса источника, календаря, доступности, окна выполнения и лимитов.
2. **Preflight:** сеть, права, место, доступность хранилища, совместимость и достаточность ключей.
3. **Prepare:** получить согласованный источник (при необходимости VSS/SQL-снимок/штатный инструмент).
4. **Capture:** считывать данные и их метаданные; фиксировать ошибки объектов.
5. **Commit:** зафиксировать адресуемый неизменяемый снимок/манифест после завершения всех обязательных частей.
6. **Verify:** проверка структуры, комплектности, доступности, контрольных сумм/проверки репозитория; результаты видны раздельно.
7. **Postprocess:** обновить индекс и каталог, отправить уведомления, освободить ресурсы.
8. **Retention:** отдельное защищённое задание, только при соблюдении условий и блокировок.
9. **Restore drill:** по расписанию или вручную проверить восстановление на выделенную цель и пометить проверенную точку.

**Состояния:** `scheduled`, `waiting_for_source`, `queued`, `preflight`, `preparing`, `capturing`, `committing`, `verifying`, `completed`, `completed_with_warnings`, `failed`, `cancelled`, `interrupted`, `stale`. Отдельные оси качества снимка: **создан**, **данные проверены**, **восстановление проверено**; нельзя свести их к одной зелёной галочке.

**Инварианты:** неполный SQL-комплект не публикуется как пригодный; отказ `mount` не превращается в успешную копию пустого каталога; очередь не выполняет один и тот же job одновременно; старые годные снимки не уничтожаются из-за ошибок нового; журнал хранит код ошибки каждого этапа; после перезапуска процесса задания примиряются с состоянием хранилища.

### 5.1. Временные ПК

Если ПК выключен — статус «ожидает доступности», без ложного «успешно». При появлении выполняется актуальное пропущенное задание; число накопившихся пропусков и правила догоняющего запуска настраиваются. Сервер не должен пытаться подключаться каждые несколько секунд: backoff, оконные проверки и общий лимит опроса. Возможны пробуждение через Wake-on-LAN только как отдельная явная опция при подходящей сети.

## 6. Нативные коннекторы источников

### 6.1. SMB/Windows/Samba

Профиль задаётся сервером, шарой/путём, диалектом SMB, учётными данными, включениями/исключениями, политикой симлинков, ожидаемыми метаданными, расписанием и скоростью. Серверные шары SMB2/SMB3 — стандарт; SMB1 — отдельный осознанный риск и изоляция. Источник может быть Windows или Samba на Linux.

**Права и атрибуты:** сохранить timestamps и данные, а также ACL, ownership, DOS-атрибуты, alternate data streams — **только при доказанной поддержке конкретного протокола/адаптера**. Интерфейс показывает уровень fidelity: `content only`, `basic metadata`, `full metadata verified`. Для полного сохранения ACL Samba на собственном Linux хосте полезнее SSH с нативными ACL/xattr, чем слепое копирование через SMB.

**Изменения во время копирования:** для обычных шар по умолчанию «best effort»: обнаруживать изменившиеся во время чтения файлы и сообщать о них. Для Windows поддерживаемый VSS-сценарий через удалённое выполнение и доступ к согласованной точке; его доступность проверяется preflight. Отсутствие VSS не маскировать.

### 6.2. Linux через SSH/SFTP

Поддержать каталоги и файлы, UID/GID, mode, симлинки, ACL/xattr (где возможно), исключения, mount boundary, лимиты пропускной способности. Аутентификация по ключам SSH с проверкой host key; root не нужен по умолчанию, повышение прав — строго ограниченное. Консистентность открытых файлов зависит от сервиса: никакой «согласованный snapshot» по голому SFTP не обещается. Профили файловых систем/снимков можно расширять отдельно.

### 6.3. PostgreSQL обычный

Нативное подключение или удалённый вызов штатных PostgreSQL-утилит без пользовательского скрипта; обнаружение версии и базы, согласованный `pg_dump`, отдельная обработка глобальных ролей и расширений, тестируемое восстановление в новую базу, ограничение нагрузки. Для 1.0 — **логические** сценарии и проверенная совместимость. Отдельный физический профиль всего кластера и PITR/WAL — P1, с явно иной моделью хранения и восстановления.

### 6.4. PostgreSQL Pro 1C и огромная `public.config`

**Нативная стратегия `postgres_1c_split_config`**, не произвольная оболочка существующего скрипта:

1. Обнаружить сервер, major version, вариант Postgres Pro 1C, имя БД, доступность `public.config`, размер и ограничения, согласовать права.
2. Получить основной согласованный логический дамп без `public.config`.
3. Сохранить DDL `public.config` с зависимостями и необходимыми метаданными.
4. Сохранить содержимое `public.config` отдельным потоковым `COPY ... WITH BINARY` с учётом требуемой версии/окружения.
5. Зафиксировать в одном манифесте три обязательные составляющие, версии инструментария, список расширений, кодировку, идентичность БД, время/правила согласованности, контрольные суммы и рецепт восстановления.
6. Проверить статус каждого этапа и комплектность; отсутствие одной части означает «ошибка», без публикации успешной точки.
7. Восстановление — на специально выбранную цель: создать новую БД с нужными ролями/расширениями, восстановить обычный дамп, создать `public.config`, загрузить бинарные данные, выполнить системные проверки и, где возможно, прикладную проверку 1С.

**Предпосылка согласованности:** конфигурация 1С во время резервирования не обновляется согласно регламенту. Если это не соблюдается, базовая схема может не дать согласованного состояния; коннектор должен поддерживать задаваемое окно, предупреждение/контроль признаков изменений `public.config` до/после, а также отдельный безопасный физический режим в последующих версиях. Изменение обычных таблиц во время `pg_dump` само по себе допускается MVCC; отдельная копия `public.config` требует именно стабильности конфигурации. Запрещено обещать универсальный транзакционно-общий снимок трёх последовательных операций.

**Совместимость:** бинарный `COPY` не принимается как универсально переносимый архив между любыми major/архитектурами. Матрицу Postgres Pro, кодировки, расширений, идентификаторов и ролей проверять на реальном восстановлении; несовместимая цель блокируется до явного экспертного решения. Рецепт восстановления версионируется вместе со снимком.

### 6.5. Thunderbird на Windows/Linux

Обнаружение всех профилей пользователя, профилей по нестандартным путям и пользовательских локальных папок; включение mailstore, адресных книг, настроек, фильтров и связанных данных. Различать IMAP- и POP3-учётные записи: локально сохранённые письма могут быть единственной копией. На Windows при открытом Thunderbird: по возможности VSS через штатное удалённое управление, с маркировкой результата как «согласованный на уровне файловой системы / crash-consistent», **не как app-consistent**, если нет соответствующего VSS-writer. Если VSS недоступен — явная политика «пропустить», «попросить закрыть приложение» или «сохранить с предупреждением»; никакой тихой деградации.

Восстановление профиля — в новый каталог/на другую машину с проверкой структуры, не перезаписывать работающий профиль без подтверждения и закрытия программы. Отдельные письма из локальных форматов — расширенная опция P1.

### 6.6. Почтовые серверы, IMAP и POP3

При полном административном доступе к Dovecot предпочтение штатному механизму `doveadm backup`/поддерживаемой серверной копии через SSH, со списком ящиков, индексами, вложениями, правами и рецептами восстановления. При отсутствии Dovecot, но при файловом доступе — специализированный профиль конкретного почтового хранилища; не копировать работающую БД вслепую.

IMAP-профиль: копирование доступных ящиков/папок/сообщений и допустимых метаданных с ведением соответствия UID/UIDVALIDITY, обработкой удалений и повторов, выборочным восстановлением/экспортом EML. UID не является вечным идентификатором письма; алгоритм должен учитывать смену UIDVALIDITY. IMAP не является полным бекапом настроек почтового сервера и всех служебных данных.

POP3-профиль: ограниченная выгрузка доступных сообщений с серверной стороны, с явным предупреждением, что история удалённых клиентом сообщений, папки и флаги недоступны. Не считать POP3 полноценным серверным резервированием.

### 6.7. Windows/AD

SMB для доступных файлов; WinRM/PowerShell Remoting для штатных операций на источнике; VSS для поддерживаемых файловых задач; Windows Server Backup/System State для контроллеров AD с проверкой роли машины и полномочий. Отдельный профиль AD, документированное восстановление контроллера и леса: это **не** восстановление NTDS и SYSVOL обычной файловой копией. В 1.0 допустимо поддержать создание/архивирование штатного System State и контролируемое развёртывание с операторской инструкцией; полностью автоматическая процедура forest recovery не обещается.

## 7. Снимки, хранение и ротация

### 7.1. Модель полного снимка

Каждая точка показывает пользователю **полное логическое дерево данных** на выбранный момент. Физически хранить полную копию каждой даты необязательно: Restic использует дедупликацию зашифрованных объектов. Все необходимые для старого снимка данные должны оставаться доступными при удалении новых/старых точек.

Снимок имеет неизменяемый ID, источник, время начала/конца, список корней, captured item count, размер исходных данных, объём новых данных в хранилище, способ согласованности, уровень метаданных, результат проверки, теги и версию рецепта восстановления. Для составных приложений — отдельный manifest с обязательными частями.

### 7.2. Политика хранения

Настройка частоты резервирования **не зависит** от срока хранения. Обязательные варианты: ежедневные, еженедельные, ежемесячные, годовые, заданный интервал/дни недели, календарный период, минимальное число копий, минимальный возраст, ручное закрепление снимка (`pin`/`hold`), «последний проверенный».

Пример: ежедневные снимки 30 дней; по одной недельной точке за 12 недель; ежемесячные за 12 месяцев. Политика считается по реальным датам; до применения показывается dry-run: что останется, что удалится. Шаблон предупреждает, если копирование делается раз в неделю, а пользователь требует ежедневных исторических точек, которых физически нет.

Принципы удаления: никогда не удалять единственную успешно проверенную копию из-за сбоя нового задания; учитывать закрепления, юридические ограничения и окна защиты от шифровальщиков; отделять удаление записи снимка от освобождения блоков `prune`; реплика должна учитываться при планировании опасной очистки; логирование обязательное.

### 7.3. Защита от шифровальщиков

- Снимки неизменяемы по смыслу; доступ к данным источников не даёт права изменять копии.
- Хотя бы одна независимая копия вне компрометируемой площадки/учётных данных. Практическая цель — схема 3-2-1 с защищённой неизменяемой или offline-копией там, где это возможно.
- Разделение полномочий записи, удаления и `prune`. Append-only репозиторий возможен только при backend, обеспечивающем ограничение прав **на самом сервере хранилища**, а не одним флажком в UI.
- Защитный период, после которого удаление возможно с отдельными полномочиями; `hold` для известных исправных снимков; запрет массового удаления без подтверждения.
- Обнаружение массовых изменений, исчезновения множества файлов, необычных расширений/энтропии — **сигнал тревоги**, а не антивирус. При подозрении можно поставить retention на паузу и уведомить, не удаляя уже созданные копии.
- Если злоумышленник получил административные полномочия на хранилище или ключи, локальное append-only само по себе не спасает: нужна независимая доверенная зона.

### 7.4. Проверка и обслуживание

Плановые проверки структуры репозитория и выборочное чтение данных, полная проверка по разумному расписанию, сверка манифестов, тестовое восстановление отдельных снимков. `prune` выполняется отдельно и не блокирует рабочее расписание неожиданно; с учётом блокировок репозитория. Система сообщает об отсутствии проверки восстановления, даже если `restic check` успешен.

### 7.5. Множественные хранилища

Каждый policy/job привязан к primary repo и при необходимости к secondary independent repo. Репликацию нужно подтверждать состоянием каждой цели; снимок может быть «локально готов, внешняя копия отстаёт». Хранилища: локальный диск, SFTP, S3-совместимое, сетевой путь через безопасный mount/адаптер. Отдельные репозитории для чувствительных групп данных с собственными ключами и retention; один общий репозиторий не должен автоматически давать всем операторам доступ ко всем данным.

## 8. Поиск, просмотр, экспорт и восстановление

### 8.1. Просмотр истории

Путь: «Источники → Шара / Пользователь / База → История → Дата → Дерево файлов». Переходы по каталогам, список версий конкретного файла, отличия снимков, фильтр `существовал/изменён/удалён`, поиск по части имени, полному пути, маске и интервалу дат. Поиск должен возвращать, например, «был в снимках до 01.10; в снимке от 08.10 отсутствует», а не обещать точную секунду удаления.

Каталог индексирует пути/имена, даты, типы и версии; FTS/SQLite и постраничная выдача. Контентный полнотекстовый поиск внутри документов **не обязателен** в 1.0. Индекс может быть пересоздан из репозитория и переносимых manifests, без потери самих копий.

### 8.2. Экспорт на ПК администратора

- Один файл: немедленная загрузка исходного файла через HTTPS.
- Одна папка: ZIP (по умолчанию) или TAR; сохранить дерево и имена.
- Произвольный набор файлов/папок: ZIP/TAR, составленный из **одного выбранного снимка** без смешивания дат.
- Полный файловый снимок: ZIP/TAR (или специализированный переносимый комплект, если это БД/приложение).
- Большие объёмы: потоковая сборка без временного двойного объёма, ZIP64, контроль отмены; подготовленный экспорт с временным файлом, сроком жизни и HTTP Range для скачивания с докачкой.
- Недостатки API выбора локальных папок в браузерах: ZIP — универсальный вариант. Нативное «выбрать локальную папку и сохранить распакованную структуру» только там, где браузер это позволяет; ни в коем случае не обещать одинаковую работу во всех браузерах.
- Имя архива содержит источник и дату; в составе — manifest (`source`, `snapshot_id`, дата, пути, контрольные суммы, предупреждение об ограничениях метаданных).
- Ограничения по ролям, максимальному объёму, времени жизни подготовленного экспорта и защита от zip-slip/path traversal. Экспорт отражён в аудите.

### 8.3. Восстановление

**Режимы:** вернуть файл/каталог на исходное место; восстановить в альтернативную папку/шару/хост; восстановить весь файловый снимок; восстановить ящик/почтовое сообщение (если формат поддерживает); восстановить базу приложения в отдельное окружение; экспортировать SQL-комплект для ручного аварийного восстановления.

**Безопасный мастер:** выбрать точку и объекты → выбрать цель → предпросмотр конфликтов и удаления → проверка прав и свободного места → dry-run → явное подтверждение → выполнение с журналом → отчёт. Для перезаписи системных данных или рабочей БД — дополнительное подтверждение, права и возможность остановить зависимые службы.

**Конфликты:** по умолчанию «в новую папку» либо «переименовать конфликтующие», никогда не уничтожать без предупреждения. `overwrite`, `skip`, `rename`, `mirror-delete` — различные явно обозначенные политики. Пользователь должен видеть, что режим синхронизации с удалением способен стереть файлы на цели.

**Проверяемость:** контроль размер/хеш, выборочная/полная функциональная проверка; отчёт отдельно различает завершение переноса и успешный запуск приложения. Восстановление на источник, который был скомпрометирован шифровальщиком, должно сопровождаться предупреждением о необходимости очистки среды.

## 9. Веб-интерфейс и UX

Основные разделы: **Обзор**, **Источники**, **Задания**, **История и поиск**, **Восстановления/Экспорт**, **Хранилища**, **События**, **Пользователи и настройки**.

### 9.1. Обзор

Показывает число источников с актуальной копией, просроченных, недоступных, ошибок, заполнение хранилищ, последнюю **проверенную** точку, запущенные задания и состояние независимых реплик. Статус защиты источника отличается от статуса последнего job.

### 9.2. Мастер добавления источника

1. Выбрать тип: SMB, Linux SSH, Windows/Thunderbird, PostgreSQL, PostgreSQL 1С, Dovecot/IMAP.
2. Адрес/порт/DNS, способ аутентификации; проверить соединение, не сохраняя пароль в лог.
3. Автообнаружение доступных шар, каталогов, баз, профилей или ящиков; ручной режим при отсутствии discover.
4. Выбрать объекты и метод. Показать доступную согласованность, требуемые права, что **не попадёт** в копию.
5. Выбрать primary/secondary repository, расписание, retention, лимиты, уведомления.
6. Проверка preflight и тестовый запуск (без автоматической активации ротации до первой успешной точки).
7. После создания — карточка со статусом, историей, восстановлением, метриками, редактированием.

### 9.3. Списки и действия

Списки должны фильтроваться по источнику, типу, состоянию, группе и месту хранения. Кнопки «Сделать копию сейчас», «Проверить», «Открыть снимок», «Скачать», «Восстановить», «Закрепить», «Показать лог» доступны в контексте, а опасные функции не маскируются под обычные. Тексты ошибок — человеческие с техническими деталями в раскрытии.

### 9.4. Доступность и локализация

Русский — полноценный язык интерфейса с первого выпуска; английский — второй. Время отображается с часовым поясом, в API хранится UTC. Адаптация под настольный браузер в приоритете; мобильный просмотр состояния обязателен, сложное восстановление может быть desktop-first. Поддержка клавиатуры, поиск в длинных списках, понятные статусы без одной только цветовой кодировки.

## 10. Доступ, учётные данные и безопасность

### 10.1. Роли (RBAC)

| Роль | Возможности |
|---|---|
| Administrator | Конфигурация, пользователи, подключение хранилищ, политики, управление ключами через отдельные защищённые процедуры |
| Backup Operator | Добавлять/редактировать назначенные источники, запускать копии, видеть журналы, без доступа к глобальным ключам/удалению хранилищ |
| Restore Operator | Просмотр разрешённых снимков, выборочное восстановление/экспорт в разрешённые места |
| Auditor | Только чтение статусов, истории и аудита; содержимое файлов по умолчанию недоступно |
| Viewer | Просмотр общей статистики без секретов, данных и экспорта |

**Доступ к данным отдельно от права управлять задачами.** Restore/Export должны ограничиваться источниками и группами; скачивание почты бухгалтерии — чувствительная операция с аудитом. Разрушительные операции — отдельный scoped privilege; возможный принцип двух подтверждений для уничтожения репозитория или снятия immutable hold.

### 10.2. Аутентификация

Первый администратор создаётся при установке через одноразовый bootstrap-token с ограниченным сроком; после настройки токен гасится. Пароль хранится через современный memory-hard KDF (например, Argon2id); сессии с CSRF-защитой, secure/httpOnly cookies, rate limits. TLS обязателен при доступе через сеть; reverse proxy Nginx поддерживается, встроенный HTTPS — возможный режим. LDAP/AD SSO и TOTP/WebAuthn — расширения, не повод хранить локальные пароли небезопасно.

### 10.3. Секреты

Пароли SMB/IMAP/БД, SSH-ключи и ключи репозиториев — в шифрованном vault SQLite/отдельном файле, master-key вне основной БД, минимальные права ОС. В интерфейсе пароль никогда не показывается повторно полностью. Модель аварийного восстановления предусматривает **отдельный recovery kit**: шифрованный экспорт конфигурации + информация о репозиториях + мастер-ключ/секрет, сохраняемый администратором вне backup-сервера. Потеря ключа означает невозможность восстановления шифрованного архива — это должно быть сказано прямо.

### 10.4. Запуск с минимумом прав

Основной процесс работает без root. Привилегированные системные операции — только через ограниченные помощники/одноразовые команды с allowlist и аудитом, без произвольных shell-команд. Для SSH — проверка known_hosts и отдельные технические учётные записи. Для WinRM — защищённое подключение и ограниченные полномочия; для старых SMB1-систем — собственный изолированный исполнитель, запрещён доступ в посторонние подсети.

### 10.5. Журналы и защита API

Аудит: входы, изменения настроек, доступ к снимкам, поиск/просмотр содержимого по необходимости, экспорты, восстановления, удаления/hold, ротация ключей, ошибки аутентификации. Не логировать пароли и содержимое почты. API: защита от SSRF при добавлении источников, path traversal, zip-slip, command injection, злонамеренных имен файлов, перегрузки входными данными и слишком больших заданий экспорта. Маскирование чувствительных путей и ограничение хранения журналов.

## 11. Хранение каталога, форматы и модель данных

Встроенная SQLite (`WAL`), схема с миграциями и резервированием самой метабазы. Минимальные сущности:

- `instance` — UUID независимого BackupHub (на перспективу объединения узлов), версия, часовой пояс.
- `source` — идентичность подключения, тип, адрес, возможности, ссылки на секреты.
- `dataset` — конкретная шара/папка/БД/почтовый профиль/ящик.
- `job` / `schedule` — источник, план, приоритет, окна, retries, лимиты.
- `job_run` / `phase` — индивидуальные запуски и этапы с кодами ошибок.
- `snapshot` / `snapshot_item` — ID снимка, репозиторий, время, пути/метаданные, контрольные суммы, статусы, формат.
- `manifest` / `restore_recipe` — версионированные правила восстановления и необходимые компоненты.
- `storage` / `replica` — backend, состояние, отставание, ключи и политики хранения.
- `retention_policy` / `hold` — правила и закрепления.
- `restore_run` / `export_run` — операции выдачи/восстановления и их аудит.
- `user` / `role` / `permission_scope` / `audit_event` — доступ.
- `notification_channel` / `notification_event` — доставка и её результат.

**Никаких абсолютных внутренних путей SQLite как единственного источника истины о копии.** Переносимый manifest вместе со снимком содержит ключевые метаданные, ID, рецепт и совместимость; должен поддерживаться импорт существующего репозитория и восстановление индекса при утрате SQLite.

Номер версии схемы/рецепта закреплён в каждом снимке; обновления приложения не должны лишать возможности восстановления старых копий. При отказе от Restic в отдалённом будущем нужен адаптер хранилища, а не миграция всех коннекторов.

## 12. API и внешние интеграции

REST API версионируется `/api/v1`, использует pagination, фильтры, scope permissions, idempotency keys для запуска заданий, события прогресса через SSE или WebSocket (вариант реализации выбирается позднее). Пример логических ресурсов:

```text
GET    /api/v1/health
GET    /api/v1/sources
POST   /api/v1/sources
POST   /api/v1/sources/{id}/test
GET    /api/v1/datasets/{id}/snapshots
POST   /api/v1/jobs/{id}/run
GET    /api/v1/runs/{id}
GET    /api/v1/snapshots/{id}/tree
GET    /api/v1/search?source=...&q=...&from=...&to=...
POST   /api/v1/exports
GET    /api/v1/exports/{id}
GET    /api/v1/exports/{id}/download
POST   /api/v1/restores/plan
POST   /api/v1/restores
POST   /api/v1/snapshots/{id}/holds
GET    /api/v1/audit
```

API должно разрешать безопасную автоматизацию, но пользовательский интерфейс остаётся основным способом работы. Уведомления о завершении/ошибке/просрочке/недоступности источника, угрозе ротации, неудачной проверке репозитория, проблемах с репликой. Webhook с подписью, повторы с ограничениями; отдельные адаптеры Telegram, ChimePort, Email. Доставка уведомления не должна влиять на результат самого бекапа.

## 13. Установка и эксплуатация

### 13.1. Debian/Ubuntu (основной сценарий)

Дистрибутив: подписанный release-архив или `.deb` с бинарником, встроенными статическими ресурсами UI, сервисом systemd и отдельной CLI для аварийного обслуживания. Директории по FHS, например:

```text
/etc/backuphub/config.yaml        # несекретные параметры процесса
/var/lib/backuphub/               # SQLite, индексы, служебные манифесты
/var/log/backuphub/               # журналы (или journald)
/var/cache/backuphub/exports/     # временные подготовленные экспорты
/backups/backuphub/               # пример локального репозитория, не жёстко задано
```

Установщик проверяет архитектуру, место/права, создаёт отдельного системного пользователя, конфигурацию, unit, bootstrap токен и печатает URL первичной настройки. Никаких отправок данных в облако разработчика. Обновление: предварительный снимок конфигурации/БД, миграции, безопасный rollback и обратная совместимость рецептов.

### 13.2. Docker/Portainer

Официальный контейнер — вариант установки, но **не** повод раздавать всем контейнерам `--privileged`. Прямой доступ к SMB/SSH/IMAP/БД из контейнера; для CIFS и VSS/Windows допустимы отдельные ограниченные внешние исполнители или сетевые коннекторы. Volume для состояния, конфигурации и временных экспортов; локальное хранилище можно монтировать отдельно. Read-only root filesystem там, где возможно; healthcheck, graceful shutdown. Документированный пример Compose для Portainer с Nginx reverse proxy.

### 13.3. Рекомендуемая топология

BackupHub устанавливается на выделенном backup-хосте в сети организации; источники не получают права удалять копии; интерфейс доступен по HTTPS только администраторам/VPN. Основной репозиторий — локальный большой диск или NAS с отдельным доступом; вторая копия — другой сервер/объектное хранилище с независимыми полномочиями и защитой от удаления. Нагрузка на источники ограничивается расписаниями и bandwidth caps.

### 13.4. Эксплуатация самого BackupHub

Система должна резервировать собственные настройки/SQLite, экспортировать конфигурацию без секретов и в защищённом комплекте с ними, проверять свободное место, писать `health`, контролировать сроки сертификатов в пределах своих компонентов, хранить настройки в человекочитаемом формате при экспорте. Приложение должно стартовать и выполнять восстановление после перезагрузки, включая реконструкцию незавершённых операций без потери истории.

**Аварийный комплект:** URL/адреса репозиториев, ключи, манифесты, совместимые CLI-утилиты, описание конфигурации, пошаговая инструкция `backuphub recovery` и независимый способ Restic. Recovery kit хранится **вне** основного сервера.

## 14. Нефункциональные требования и метрики

Значения ниже — **проектные цели, подлежащие нагрузочному тестированию**, а не заявления о достигнутой производительности.

- На типовом выделенном Linux-хосте GUI и планировщик должны работать при ограниченной оперативной памяти без внешнего DB/брокера; ориентир для idle основного процесса до 300 МБ без тяжёлых заданий/индексации, уточняется тестами.
- Минимальный сценарий: десятки источников и миллионы файлов в репозиториях, постраничные списки и ленивый индекс; не загружать всё дерево в браузер.
- До 4 одновременных сетевых заданий по умолчанию, настраиваемый лимит по источнику/хранилищу и скорости, исключение конкурирующих опасных операций.
- API списков при обычной нагрузке ориентир p95 до 500 мс на локальном сервере, сложный поиск/индексация допускаются асинхронно с прогрессом.
- Для больших ZIP поддерживать ZIP64 и потоковую выдачу; подготовленные экспорты должны поддерживать HTTP Range, проверку пространства и TTL; максимальный допустимый объём настраивается.
- Цели RPO/RTO **назначает администратор для каждого dataset**: программа показывает достижимость по расписанию, последней годной копии и тестам восстановления, но не обещает универсальные значения.
- Отсутствие соединения с источником не нарушает работу других заданий; программа остаётся управляемой при сбое хранилища и показывает причину.
- Документация и тесты безопасности, миграции, режим без телеметрии по умолчанию.
- Open source: рекомендуемый вариант лицензии Apache-2.0 или AGPL-3.0; окончательный выбор — отдельное проектное решение до первого публичного релиза с учётом лицензий зависимостей.

## 15. Критерии приёмки 1.0

Ниже — тесты в реальной стендовой инфраструктуре; для каждого обязательны протокол, ожидаемый результат и сохранённые артефакты. Запуск набора тестов на демоданных не заменяет восстановление реальных объектов.

| ID | Проверка | Критерий |
|---|---|---|
| AT-01 | Чистая установка на Debian | Один сервис, первичная настройка в браузере, без внешней БД и ручной сборки скриптов |
| AT-02 | Добавить SMB2/3-шару | Подключение и первый полный логический снимок из UI |

| AT-06 | Ротация | План dry-run, сохранение закреплённых и единственной годной копии, корректное освобождение блоков |
| AT-07 | Шифровальщик (имитация) | Восстановление папки из даты до массового изменения, сохранение прежнего снимка |
| AT-08 | Скачать `Video` | ZIP содержит точное дерево из выбранной даты, скачивание через браузер |

| AT-10 | Скачивание большого архива | ZIP64 и проверяемый подготовленный экспорт с возобновлением |
| AT-11 | Linux SSH | Сохранены и корректно восстановлены доступные mode/UID/GID/symlink/ACL согласно заявленному уровню |
| AT-12 | ПК офлайн | Пропуск без ложного успеха, догоняющий запуск после доступности |
| AT-13 | Thunderbird | Профиль восстановлен на тестовом ПК, корректно запускается Thunderbird; несогласованный режим помечен |
| AT-14 | PostgreSQL обычный | Снимок и успешное восстановление в новую тестовую базу |
| AT-15 | PostgreSQL 1С | Нативный split-config с большим `public.config`, все части проверены, база восстановлена без старого скрипта |
| AT-16 | Ошибка одного этапа 1С | Снимок не помечен годным; старые годные точки не удалены |
| AT-17 | Dovecot/IMAP | Сохранение и возврат выбранного ящика или сообщения в пределах заявленного метода |
| AT-18 | AD System State | Штатная копия с отчётом и документированной стендовой процедурой восстановления, без ложной декларации «полное авто-восстановление леса» |
| AT-19 | Тестовый restore | Отдельно фиксируется «данные целы» и «приложение запустилось» |
| AT-20 | Независимость от UI | Restore из репозитория без работающего BackupHub и с recovery kit |
| AT-21 | Компрометация source | Пользователь источника не может удалить старые защищённые копии |
| AT-22 | Второй репозиторий | Подтверждение полноты репликации; поломка одного backend не обманывает мониторинг |
| AT-23 | Права и аудит | Viewer не может читать содержимое, Restore Operator ограничен scopes; экспорт протоколируется |
| AT-24 | Никаких legacy-скриптов | Все штатные сценарии 1.0 выполняются нативными коннекторами, cron не нужен |
| AT-25 | Recovery системы | Утрата SQLite/сервера; импорт репозитория и перестройка каталога/восстановление данных |

**Release gate:** ни один P0-критический тест не должен быть закрыт фразой «выполнить существующий скрипт». Для спорных платформ допускается честно ограничить матрицу поддерживаемых версий и не выпускать соответствующий коннектор до готовности.

## 16. План разработки (внутренние этапы; не замены функций)

**Фаза A. Фундамент:** модель источников, роли и секреты, первичная установка, SQLite/migrations, Restic abstraction, snapshot manifest, scheduler, журнал, безопасное восстановление конфигурации. Проверки восстановления репозитория.

**Фаза B. Файлы и история:** нативные SMB2/3 + Linux SSH, изолированный SMB1, хранение, ротация/hold, сравнение снимков, поиск, экспорт одного файла/папки/набора/полного снимка, восстановление файлов. На этой фазе уже есть сквозной реальный workflow.

**Фаза C. Приложения:** нативный PostgreSQL и PostgreSQL 1С split-config с тестовым восстановлением, Thunderbird/WinRM/VSS, Dovecot/IMAP, Windows System State (подтверждённый уровень поддержки), специфические манифесты приложений.

**Фаза D. Надёжность и выпуск:** независимая реплика, append-only/immutability, восстановление после потери backup-хоста, автоматические контрольные восстановления, безопасность, нагрузочное тестирование, документация, установочные пакеты, acceptance матрица из раздела 15. **Публичный 1.0 только после прохождения обязательных сценариев.**

**После 1.0:** расширенная работа с ACL/ADS, физические PostgreSQL+PITR, LDAP/SSO/MFA, portable-helper при объективной потребности, более сложные почтовые форматы, custom script-коннектор для нестандартных заданий, Windows bare-metal recovery. Приоритеты пересматриваются по реальным тестам, не меняя основных инвариантов.

## 17. Несколько BackupHub-узлов — будущее, не зависимость

В 1.0 каждый instance имеет собственный `instance_uuid`, БД, секреты, репозитории, пользователей и политики. У одного пользователя могут быть две независимые установки — по одной для каждой организации. В перспективе возможен **Fleet View**: один выбранный BackupHub отображает список других узлов, их статусы, ошибки, объёмы и последние точки, затем (после отдельного threat model) управляет заданиями через делегированные scoped credentials.

**Не входит в 1.0:** общий DB-кластер, единый обязательный coordinator, сквозные учётные записи, репликация секретов и automatic cross-site restore. Сеть между организациями не требуется для основной функции. Протокол будущего fleet-режима должен обеспечивать автономность, явное доверие, TLS, отзыв узла и отдельную модель полномочий.

## 18. Риски, компромиссы и открытые решения

| Риск/выбор | Решение по умолчанию / что проверить |
|---|---|
| SMB1 опасен | Только явное включение для конкретного источника, изолированный исполнитель, сетевые ACL, отдельная техническая учётная запись |
| SMB/SSH не даёт согласованности приложения | Показывать fidelity; использовать VSS/штатные методы, где необходимо; не выдавать best effort за app-consistent |
| Thunderbird открыт | Windows VSS = crash-consistent без app-writer; требуется тест восстановления и явная деградация |
| PostgreSQL 1С split-config | Нативный механизм, регламент без обновления конфигурации, проверка неизменности config, тесты на Postgres Pro 1C 16 и переносимость `COPY BINARY` |
| Restic общий репозиторий | Несколько репозиториев там, где нужен контроль доступа и retention; набор настроек не должен блокировать dedup внутри репозитория |
| Индекс большой | Поэтапная индексация, SQLite FTS/пагинация, импорт/перестройка из manifests |
| BackupHub/ключи скомпрометированы | Внешний immutable/offline backup и разделение delete/append credentials; локальный hold без внешней защиты недостаточен |
| Тяжёлый экспорт | Потоковый ZIP/TAR и отдельно подготовленный экспорт с TTL/range; контроль квот и свободного места |
| Копирование по сети без агента | Возможна высокая передача неизменённых данных; явные bandwidth caps, оптимизация позже; никаких ложных обещаний эффективности |
| Один файл приложения как «восстанавливаемый» | Коннектор обязан знать состав и рецепт восстановления, а не только байты |
| Версии Windows/SMB/PostgreSQL | Публиковать конкретную поддерживаемую матрицу после integration tests; старые несовместимые версии явно вне поддержки |
| Выбор лицензии | Решить до первого публичного репозитория/релиза после аудита зависимостей |

**Нерешённые продуктовые параметры, не мешающие начать проектировать:** окончательное имя; лицензия; точная минимальная версия Windows/SMB/Thunderbird/Dovecot/Postgres Pro; количественные показатели нагрузки; профиль TLS по умолчанию; тонкости упаковки Docker-хелперов. Эти параметры должны получить отдельные ADR и реальные тестовые стенды, а не молча определяться по ходу реализации.

## 19. Предварительные архитектурные решения (ADR)

- **ADR-001:** модульный монолит Go + UI без внешнего брокера/СУБД — *принято для проектирования*.
- **ADR-002:** agentless-first; удалённое выполнение только штатными каналами — *принято*.
- **ADR-003:** Restic как проверенный базовый snapshot/storage engine за адаптером — *предпочтение, подтвердить интеграционными тестами*.
- **ADR-004:** логически полные исторические снимки + дедупликация + закрепления — *принято*.
- **ADR-005:** нативные PostgreSQL 1С, SMB и другие P0-коннекторы, не legacy scripts — *принято*.
- **ADR-006:** одна независимая установка на площадку; fleet view позже — *принято*.
- **ADR-007:** экспорт через браузер (ZIP/TAR) и отдельная модель восстановления — *принято*.
- **ADR-008:** отдельный защищённый контур удаления/ротации и внешняя копия — *принято как требование, backend выбрать*.
- **ADR-009:** скрипты только в дополнительном plugin-type после базового релиза — *принято*.

## 20. Документация, которая должна поставляться с продуктом

1. Быстрая установка Debian/systemd и Docker/Portainer.
2. Минимальные сетевые порты и права для каждого коннектора.
3. Подготовка Windows/WinRM/VSS и отдельная документация по AD System State.
4. Настройка SMB1 в изоляции и предупреждения по безопасности.
5. PostgreSQL и PostgreSQL 1С: совместимость версий, создание, восстановление, контрольные проверки, лимиты больших `public.config`.
6. Thunderbird: профили, POP3/IMAP, копирование работающих профилей и ограничения.
7. Dovecot/IMAP/POP3: полнота резервной копии и сценарии восстановления.
8. Политики хранения, hold, внешняя репликация, борьба с шифровальщиками.
9. Поиск, экспорт файлов/папок, восстановление и разрешение конфликтов.
10. Восстановление при уничтожении сервера BackupHub, recovery kit, ключи, CLI и восстановление без UI.
11. Аудит, RBAC, безопасность, обновления/откат, troubleshooting.
12. Совместимость и отчёты реальных проверок восстановления для каждого поддерживаемого типа.

---

**Итог:** BackupHub — не оболочка над cron и не уменьшенная копия Veeam, а лёгкий независимый продукт с нативными коннекторами, логически полными историческими снимками, безопасным хранением и полноценным восстановлением/экспортом через браузер. Первая полноценная версия должна решать реальные сценарии двух организаций без пользовательских скриптов. Возможность объединения нескольких автономных BackupHub откладывается на будущее без технической зависимости от неё сегодня.
