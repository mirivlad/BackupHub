# BackupHub Preview 4 — аварийное восстановление

## Сценарий A: погиб системный диск, остались диски Restic

1. Установить BackupHub на чистую машину, создать администратора (для доступа к браузеру).
2. Подключить физические диски с архивами и смонтировать их в `/mnt`, `/media`, `/backup`, `/backup2` или `/srv/backups`. Убедиться, что *именно настоящий том* смонтирован — не пустая точка монтирования.
3. В веб-интерфейсе открыть **«Аварийное восстановление»** и выбрать существующую **родительскую папку**, где находится `repository/config` (не сам `repository`).
4. Выбрать режим: «Без пароля» (только диск) или «С паролем». Для парольного предоставить **оригинальный** файл `restic-<id>.key` старого сервера (для старого primary — `restic.key`).
5. Нажать **«Подключить и восстановить историю»**. BackupHub не вызывает `restic init` и не форматирует архив, проверяет структуру Restic и восстанавливает индекс из независимых commit-маркеров.
6. Открыть раздел истории, выбрать нужные файлы/папки, скачать через браузер или восстановить в отдельный каталог.

Восстанавливаются **только завершённые** снимки, имеющие `bh-commit-<id>` и ссылку на действительный снимок с данными. Неизвестные/битые/несогласованные маркеры отклоняются. Время и имя берутся из переносимого манифеста. Проверка при импорте `restic check` проверяет метаданные репозитория, **не перечитывает весь объём файлов**; первоначальная полная проверка проводилась при создании снимка.

**Важные ограничения:** исходные пароли сетевых источников, расписания и роли восстановить только из commit-маркеров нельзя. Такие источники импортируются как архивная история **без активных заданий**. После импорта настройте рабочие источники заново. Исторические записи останутся доступны, но новые задания пока не объединяются автоматически со старыми ID. Беспарольное хранилище может быть прочитано без `master.key`; для парольного нужен ключ.

### Права каталога после переноса

Привилегированный helper подключает только существующие папки, уже принадлежащие сервисному пользователю `backuphub` (UID/GID сервера) с правами 0700, и **не меняет владельцев существующих архивов**. Если другой компьютер выделил пользователю `backuphub` иной UID, администратор отдельно настраивает права только нужного backup-каталога. Не запускайте рекурсивный `chown` по всему чужому диску без проверки.

## Сценарий B: заранее сохранён Recovery Kit — вернуть конфигурацию

**Recovery Kit не содержит сами большие Restic-архивы.** ZIP включает согласованный SQLite `catalog.db`, `master.key`, `restic.key`, все зарегистрированные ключи парольных внешних репозиториев и `recovery-manifest.json`.

В старом действующем BackupHub: администратор → **«Аварийное восстановление» → «Скачать Recovery Kit»**. Храните архив *вне* сервера BackupHub, в защищённом месте. Это **секретный комплект**, позволяющий открыть сохранённые пароли источников и защищённые копии.

Для примера восстановления на новом Debian с уже установленным BackupHub:

```bash
# 1. Важно: сервер BackupHub должен быть остановлен.
sudo systemctl stop backuphub

# 2. Копируем Recovery Kit в личный каталог сервиса.
sudo install -o backuphub -g backuphub -m 0600 ./backuphub-recovery-UUID.zip \
  /var/lib/backuphub/emergency-kit.zip

# 3. Распаковываем только в НОВЫЙ каталог (команда никогда не перезаписывает).
sudo runuser -u backuphub -- backuphub recovery-kit-restore \
  -kit /var/lib/backuphub/emergency-kit.zip \
  -data-dir /var/lib/backuphub/recovered

# 4. Перед заменой убедитесь, что архива /var/lib/backuphub.fresh НЕТ.
#    Команды ниже сохраняют исходную установку, а не удаляют её:
sudo mv -T /var/lib/backuphub /var/lib/backuphub.fresh
sudo mv -T /var/lib/backuphub.fresh/recovered /var/lib/backuphub

# 5. Подключаем выжившие диски к их ПРЕЖНИМ путям в каталоге.
sudo systemctl start backuphub
sudo systemctl status backuphub
```

Перед запуском убедитесь, что старые тома действительно смонтированы в их старых местах. При отсутствии старого `primary` BackupHub запускается в **degraded recovery mode**: не создаёт подменный архив и не может восстановить потерянные первичные снимки, но позволяет работать с сохранёнными внешними репозиториями. Оригинальная SQLite может хранить задания и для недоступных дисков: они будут завершаться ошибками, пока вы не остановите их или не вернёте том.

Не переносите системные ключи в виде публичного вложения, тикета или незашифрованной сетевой папки. ZIP Recovery Kit **сам по себе не шифруется**; защита передачи — HTTPS, защита хранения — ответственность администратора. Сохраняйте ключи независимо от резервного сервера.

## Что делает CLI-проверка Recovery Kit

`backuphub recovery-kit-restore` до распаковки проверяет формат ZIP, запрещает лишние имена и traversal, дубли и подозрительные размеры, требует основные ключи и manifest, создаёт файлы приватными (0600) и каталог 0700, сверяет `instance_uuid` и `PRAGMA quick_check` SQLite. При ошибке удаляет только вновь созданный временный каталог. **Не принимает целевой каталог, если тот уже существует**.

## Ограничения Preview

- Это Preview, не 1.0. Восстановимость каждого источника необходимо проверять отдельно.
- Нельзя автоматически восстановить потерянный архив `primary`: если он был только на погибшем системном диске, данных в нём нет.
- Restic-путь `repository` внутри выбранного каталога фиксирован; штатный интерфейс не импортирует произвольный формат чужого Restic без BackupHub-маркеров.
- Нет полного автоматического мастера восстановления ключей/работающих подключений через браузер, замены системной SQLite онлайн, автоматических повторных restore-drills.
- Для удержания истории и защиты от заполнения дисков следующий этап — Preview 5 с безопасной ротацией.
